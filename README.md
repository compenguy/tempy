# Matter Temperature/Humidity Sensor

## Sensors

This application uses the BME280 sensor as a Matter-enabled temperature and
humidity source. Readings are published as Matter attribute updates over
Thread; the initial commissioning happens over BLE (CHIPoBLE) and BLE is
released once commissioning completes.

This application creates the temperature sensor on endpoint 1, and the
humidity sensor on endpoint 2.

See the [docs](https://docs.espressif.com/projects/esp-matter/en/latest/esp32/developing.html)
for more information about building and flashing the firmware.

### Connecting the sensors

- Connecting the BME280, temperature and humidity sensor

| ESP32-H2 Pin | BME280 Pin |
|--------------|------------|
| GND          | GND        |
| 3V3          | VCC        |
| GPIO 13      | SDA        |
| GPIO 14      | SCL        |

**_NOTE:_**
- Above mentioned wiring connection is configured by default in the Kconfig
- Ensure that the GPIO pins used for the sensors are correctly configured through menuconfig.
- Modify the configuration parameters as needed for your specific hardware setup.

The BME280 module used with this project includes 10k pullups on CSB, SDI, and
SCK, plus a 10k pulldown on SDO. In I2C mode, SDI is SDA and SCK is SCL, so the
module already provides pullups for the I2C signal lines. Additional external
pullups are typically not needed for short wiring to a single sensor, but may be
useful if the bus has longer leads, more devices, or unreliable edges.

The SDO pulldown straps the BME280 I2C address to `0x76`, which is the default
configured by this project. If using a different module or tying SDO high,
change the BME280 I2C address in menuconfig to `0x77`.

Be aware that IO10-14, and IO22 are generally the safest to use as the others are typically
involved in flash communication, USB I/O, UART serial console, or function as strapping pins during
boot, but consult your board/chip documentation to be sure.

[This page](https://www.espboards.dev/esp32/esp32-h2-super-mini/) has a useful reference for the
ESP32-H2 Super Mini.

## Build & flash workflow

Prerequisites:
* python3-venv, python3-dev, libssl-dev (esp-idf and esp-matter-mfg-tool prereqs)
* [esp-idf](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/get-started/index.html) installed
* [esp-matter](https://docs.espressif.com/projects/esp-matter/en/latest/esp32/developing.html) installed

Everything below is driven by the `go.sh` wrapper, which activates the esp-idf
and esp-matter environments and forwards to `idf.py` or `esptool.py` as needed.

Run `./go.sh --help` for the current list of subcommands.

### Firmware image

Configure, build, and flash the app image. This is what changes on every code
change; the layout of the device's flash otherwise stays the same.

```
$ ./go.sh --menuconfig        # interactive Kconfig tweaks (optional)
$ ./go.sh --reconfigure       # regenerate sdkconfig from sdkconfig.defaults*
$ ./go.sh --build             # produces build/tempy.bin
$ ./go.sh --flash --monitor   # writes the app; opens serial console
```

`--reconfigure` regenerates `sdkconfig` from scratch and discards any
interactive `--menuconfig` changes; re-run `--menuconfig` after to reapply
those. `--full-flash` (`-F`) is the "erase everything and start over"
variant. Use it when the partition table changes or when a stale bootloader
is suspected. It also erases the factory-data partition, so a `--mfg-flash`
pass is needed before the device can be commissioned again.

### Per-unit factory data

This project is configured to read the Matter commissioning credentials from
the `fctry` NVS partition rather than from CHIP's compile-time test defaults.
Each physical unit needs its own factory-data blob written to that partition
before it can be commissioned; without it, the device boots but reports its
`MeasuredValue` as null and rejects commissioning attempts.

Factory data is generated by
[esp-matter-mfg-tool](https://github.com/espressif/esp-matter-tools) and
contains:

* A unique passcode + discriminator (replacing the `20202021` / `3840` test
  defaults that anyone on the internet can commission against)
* A unique serial number, rotating device ID, and manufacturing date
* The vendor name, product name, product label, product URL, hardware
  version, and hardware version string surfaced through the Matter Basic
  Information cluster
* A per-unit Device Attestation Certificate (DAC) signed by the project's
  Product Attestation Intermediate (PAI), plus the Certification Declaration
  (CD) that names this VID/PID pair

Generate and flash one unit:

```
$ ./go.sh --mfg-gen            # produces mfg/out/fff1_8000/<uuid>/
$ ./go.sh --mfg-flash          # writes newest to fctry @ 0x3E0000
```

Or provision a batch (e.g. 20 boards for an assembly session):

```
$ ./go.sh --mfg-gen 20         # 20 per-unit blobs under mfg/out/
# ... then for each board, connect it and run:
$ ./go.sh --mfg-flash mfg/out/fff1_8000/<that-unit's-uuid>/<uuid>-partition.bin
```

The onboarding codes for each unit (QR-code string, manual pairing code,
passcode, discriminator) are written to
`mfg/out/fff1_8000/<uuid>/<uuid>-onb_codes.csv`, and a scannable QR-code
PNG is generated alongside as `<uuid>-qrcode.png`. Keep these with the
physical unit -- either printed on the enclosure, or archived against the
serial number -- since they're the only way to commission that specific
device to a fresh fabric.

On the first `--mfg-gen` run, the script synthesizes a Certification
Declaration for the project's VID/PID using CHIP's test CD-signing key. That
needs the `chip-cert` host tool from the CHIP Linux SDK, which takes a few
minutes to build the first time. `go.sh` will prompt before running the
build; subsequent `--mfg-gen` runs reuse the cached CD.

> **Attestation trust boundary.** The DAC chain baked in by `--mfg-gen`
> terminates in CHIP's public test roots. `chip-tool` and other developer
> tools accept it; production commissioners (Apple Home, Google Home,
> SmartThings, ...) will reject it because the CSA test roots aren't in
> their attestation stores. This is the intended trade-off for "everything
> short of Matter certification" -- each unit has unique credentials, but
> the whole chain is still openly signed. Real certification requires a
> CSA-issued VID + PAI + CD; when you're ready, swap `MFG_PAI_*` and
> `MFG_CD_*` in `go.sh` and re-run `--mfg-gen`.

### Release workflow (recommended sequence)

For a brand-new board coming off the bench:

```
$ ./go.sh --reconfigure --build   # firmware
$ ./go.sh --full-flash            # bootloader + app + partition table
$ ./go.sh --mfg-gen               # per-unit factory data
$ ./go.sh --mfg-flash             # writes fctry.bin @ 0x3E0000
$ ./go.sh --monitor               # verify: boot log should show the
                                  # real vendor / product / serial / codes
```

For a firmware refresh on a board that's already been provisioned:

```
$ ./go.sh --build --flash          # app image only; fctry + nvs preserved
```

`--flash` never touches the `fctry` partition, so per-unit credentials
survive firmware updates. Only `--full-flash` (`-F`) wipes the device.

### Factory reset & re-commissioning

`--reset-fabric` erases just the runtime NVS partition (fabric table, ACLs,
subscription bookkeeping) without touching either the app image or the
factory-data partition. The device boots as un-commissioned, ready to pair
onto a new fabric using the same onboarding codes as before.

```
$ ./go.sh --reset-fabric           # prompts before erasing
```

Use this when moving a sensor between Thread networks or hand-provisioning
a replacement border router. If instead the device is physically wiped
(`--full-flash`), you'll need to re-run `--mfg-flash` before it can be
commissioned again, because the per-unit passcode / DAC will have gone
with the flash contents.

## Usage

Commission the app using a Matter controller and read the attributes. The
example below uses `chip-tool` to commission over BLE-to-Thread and then
subscribe to the sensor attributes.

The passcode and discriminator come from the per-unit onboarding codes CSV
(see [Per-unit factory data](#per-unit-factory-data) above). If you're
running with `--mfg-gen` output, look up the values for your specific
`<uuid>-onb_codes.csv`. If you skipped factory-data provisioning entirely
and are still on CHIP's compile-time defaults, use `20202021` and `3840`.

```
# Commission over BLE onto an existing Thread network. Replace
# <hex-dataset> with the operational dataset of your Thread network
# (chip-tool otbr get-active-dataset-tlvs, or from your Border Router),
# and <passcode>/<discriminator> with the values from this unit's
# onboarding codes CSV.
chip-tool pairing ble-thread 1 hex:<hex-dataset> <passcode> <discriminator>

# Start chip-tool in interactive mode
chip-tool interactive start

# Subscribe to attributes (node 1, min 3s, max 10s, endpoints 1 and 2)
> temperaturemeasurement subscribe measured-value 3 10 1 1
> relativehumiditymeasurement subscribe measured-value 3 10 1 2
```

Alternatively, scan the `<uuid>-qrcode.png` from a Matter mobile app to
commission through the same BLE-to-Thread flow.
